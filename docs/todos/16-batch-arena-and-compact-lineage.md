# Batch-Scoped Identity & Compact Lineage (design spec)

Status: **design direction locked; not yet implemented.** The current
`PortBatch` remains the compatibility data model while the unified executor is
stabilized. This spec is the substrate required before true stage-global
deferred recovery and million-record lineage claims.

Related:

- recovery scheduling: [`15-recovery-tiers-and-retry-scheduling.md`](15-recovery-tiers-and-retry-scheduling.md);
- partial replay: [`08-lineage-guided-partial-replay.md`](08-lineage-guided-partial-replay.md);
- relation algebra / reorder safety:
  [`13-reordering-invariance-theorem.md`](13-reordering-invariance-theorem.md).

## 1. Locked design decisions

1. **Runtime identity is batch-scoped, not globally permanent.**
   The coordinator creates one UUID per admitted logical microbatch.
2. **All input ports of one microbatch share the same `BatchId`.**
   `mg.source()` must not independently invent batch UUIDs.
3. **A record is addressed by a compact handle**:
   `RecordHandle = (BatchId, PortId, RowIndex)`.
4. **Batch completion is the memory reclamation boundary.**
   Once all downstream consumers, retries, output commits, and requested trace
   materializations are done, the whole batch arena can be released.
5. **Logical lineage paths are hash-consed/interned.**
   Records store a small `path_id`, not a copied Python tuple/dict per stage.
6. **External business identity is separate.**
   A source key/path may be stored optionally for checkpointing or cross-run
   queries, but it is not the default internal runtime identity.

## 2. Identity model

```text
BatchId      = UUID128
PortId       = compact integer assigned by compiled IR
RowIndex     = invocation-local integer
RecordHandle = (BatchId, PortId, RowIndex)
```

The UUID is generated by `ExecutionCoordinator` when admitting a microbatch and
is preserved through physical sharding, LPT reordering, retries, deferred drain,
fan-out, and fan-in. A legal physical reorder never creates a new `BatchId`.

Why not `name:index`?

- indices restart in every physical chunk and collide across active batches;
- stage-global quarantine/recovery could attribute a failed row to the wrong
  document;
- globally unique string IDs allocate and copy far more memory than a UUID plus
  compact integers.

Why not a required stable source key?

- many runtime objects have no durable business key;
- cross-run stability is unnecessary for ephemeral scheduling;
- it conflates runtime identity with checkpoint/catalog identity.

For persistence, store an optional `ExternalKey` alongside the source row or in
the lineage backend. On resume, the checkpoint restores the original `BatchId`
or records an explicit old→new execution mapping.

## 3. `BatchArena`: ownership and lifecycle

```text
coordinator admits input
  → BatchArena(UUID)
      values / Ray ObjectRefs
      compact record columns
      path table
      relation tables
      errors/quarantine handles
  → nodes consume/produce slices by RecordHandle
  → retry/deferred drain holds arena references
  → graph outputs committed/materialized
  → consumer + recovery reference count reaches zero
  → optional compact lineage snapshot
  → release entire arena
```

The arena is a **logical ownership unit**, not a payload-copying central actor:

- large values remain in Ray's object store;
- the driver coordinator retains handles and compact metadata;
- actors receive slices/handles needed for one invocation;
- no global lineage collector actor is introduced.

An arena cannot be released while:

- a node invocation or downstream consumer references it;
- a deferred quarantine item may be retried;
- a `Reduce`/`Relate` barrier still needs its relation table;
- output commit has not completed;
- the user requested post-run trace materialization.

User-facing `ErrorTrace` must materialize the small display/error fields it needs
before arena release; it must not contain a dangling pointer into freed metadata.

## 4. Low-rank lineage representation

The current MVP copies per row:

```text
ancestors: dict
ancestor_display: dict
ordinals: dict
lineage: tuple[str, ...]
relations: tuple[ParentRef, ...]
```

For a million rows traversing the same `Map A → Map B → Map C`, this creates a
matrix with many repeated rows. Its structural rank is low: the operator path is
shared, while records differ mainly in row/parent coordinates.

### 4.1 Hash-consed path table

```text
LineagePathTable:
  path_id -> (parent_path_id, op_id, relation_kind)

intern(parent_path_id, op_id, relation_kind) -> path_id

RecordMeta:
  handle
  path_id
  relation_ref
  ordinal_ref
```

Interning uses structural hash + equality verification (hash collision must
never merge unequal paths). Complexity changes from roughly
`O(records × 1:1 stages)` path objects to `O(unique paths + records)` compact
indices.

### 4.2 Relation-specific compact encodings

| relation | compact representation |
|---|---|
| 1:1 Map | shared `path_id`; row coordinate preserved |
| Filter | survivor row-index vector / bitmap |
| 1:N Expand | `parent_row[]` + `child_ordinal[]`; no ancestor dict per child |
| N:1 Reduce | anchor row + descendant ranges/index vector |
| multi-output | shared invocation/path table; distinct `PortId` |
| M:N Relate | CSR-style offsets + parent handle arrays per role |

The M:N edge count is irreducible (`O(edges)`), but Python object overhead is
not: CSR/columnar arrays replace per-output tuples of `ParentRef` objects.

Display keys are a separate optional column. They are not required for
scheduling correctness and may be lazily/materially retained according to trace
policy.

## 5. Correctness and semantics

- **Value-purity remains the theorem assumption.** UUID/handles are framework
  metadata and never enter UDF inputs.
- **Reordering invariance:** physical planners permute row vectors but preserve
  `RecordHandle` and relation coordinates.
- **Deferred recovery:** quarantine stores a handle into a still-live arena;
  successful retry writes back to the same logical handle.
- **Batch independence:** a `Reduce`/`Relate` that is invocation-local must not
  silently join across arenas. Cross-batch operations require an explicit
  state/window/materialization contract.
- **Persistence is opt-in:** ephemeral runs free arenas; checkpoint/lineage
  sinks serialize compact tables and execution IDs.

---

## 6. Compatibility surface

Do not force users or UDFs to adopt handles:

- `PortBatch.values` remains the UDF-facing value column;
- existing `record_ids`, `ancestors`, `ordinals`, `lineage`, and `relations`
  become compatibility views/materializations over arena tables;
- tests first compare old and compact representations for identical public
  values, trace views, grouping, and errors;
- only after parity may hot execution stop eagerly constructing legacy Python
  objects.

This avoids a flag-day rewrite of primitives, executor, and MinerU.

## 7. Incremental implementation plan

1. **Instrumentation first:** measure current lineage bytes/object counts and
   allocation time (E4 baseline).
2. **Batch identity:** coordinator-owned UUID + `BatchContext`; no UDF/API
   behavior change.
3. **1:1 path interning:** implement `LineagePathTable`; retain legacy views.
4. **1:N columnar relation:** migrate Expand parent/ordinal metadata.
5. **Reduce + error lookup:** grouping/cascade consume compact tables directly.
6. **M:N CSR:** migrate `Relate` parent evidence.
7. **Arena refcount/release:** tie lifecycle to coordinator completion,
   deferred drain, and output commit.
8. **Optional persistence:** compact lineage sink/checkpoint format.

Only after steps 2–7 should recovery doc 15 call its drain scope truly
stage-global across multiple active microbatches.

---

## 8. Required tests and measurements

- UUID unique across simultaneously active microbatches; all ports of one
  microbatch share it.
- sharding/reordering/retry preserve handles.
- arena is not freed while a deferred item or fan-in consumer exists.
- arena is released after completion (weakref/resource-counter test).
- identical 1:1 paths intern to one `path_id`.
- hash collision path verifies structural equality.
- old vs compact lineage property tests for Map/Filter/Expand/Reduce/Relate.
- M:N CSR round-trip and multi-output coverage.
- E4: bytes/record, Python object count, allocation CPU, serialization bytes,
  and end-to-end throughput from 7k pages to million-record synthetic scale.

Acceptance target: lineage memory grows with **records + unique paths + relation
edges**, not `records × path length` Python objects.
