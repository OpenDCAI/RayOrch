## 1. 命名原则

保留能直接表达语义的名称，只修改有实际歧义的词。统一引用、状态和报告的后缀，不要求数据与计算概念具有相同词尾。论文提供语义依据，映射集中说明。

业务用户主要接触 Pipeline、UDF 声明和 Port；运行时维护者再了解 Grain、身份引用、状态及执行批次。不要求用户先学完全部内部类型才能接入推理框架。

## 2. 核心词表

| 名称 | 明确含义 | OCR 例子 |
| --- | --- | --- |
| Pipeline | 用户声明的数据流 | 文档展开、OCR、按文档归并 |
| UDF | 用户提供的计算实现 | OCR 类及其批处理方法 |
| RayModule | UDF 及初始化、输出和执行配置的声明；当前先保留名称 | `self.ocr = RayModule(OCR)` |
| Call | 声明图中的一次完整算子调用，连接全部输入和输出 | `self.ocr(pages)`；不是某个参数或返回值位置 |
| Domain | 编译期的数据粒度及身份空间 | 文档域、某次展开产生的页面域 |
| Entity | 某个 Domain 中的逻辑实体 | 文档 A 的第 1 页 |
| Port | 图中的逻辑数据端口，关联一个 Domain | 页面图像端口、OCR 结果端口 |
| Item | 某个 Entity 在某个 Port 上的数据项，承载值或结果状态 | 第 1 页的 OCR 结果 |
| Grain | 某个 Call 对某个 Entity 的一份逻辑计算，身份不随重试改变 | 对第 1 页执行 OCR |
| Expansion | 某个父 Entity 在某个子 Domain 中的有序展开结果，记录成员与终态 | 文档 A 展开的全部页面；空集合可以成功 |
| InputBatch | 一批源输入及其独立运行状态和全部派生工作 | 一批文档及其展开、OCR、归并工作 |
| ExecutionMicrobatch | 同一 InputBatch、同一 Call 中组织给 Worker 执行的一组 Grains | 一次送入 OCR 的若干页，可跨文档 |

Item 表达数据，Grain 表达计算粒度，名称无需对称。Domain、Entity、Expansion 负责不同的身份与成员关系，建议保留现有名称。核心词表到此收敛，后续以具体误解或维护问题作为改名依据。

两种批的边界：InputBatch 管理源输入的生命周期；ExecutionMicrobatch 按就绪 Grains 动态组装，不跨 InputBatch。执行微批有大小上限，但不承诺固定大小或必须凑满；其页面数量可以多于输入批的文档数量。

## 3. 引用与二元坐标

`XXXRef` 表示 XXX 的身份引用，字段显式说明构成身份的坐标：

```python
GrainRef(call=call_ref, entity=entity_ref)
ItemRef(port=port_ref, entity=entity_ref)
ExpansionRef(child_domain=domain_ref, parent_entity=parent_ref)
```

PortRef 标识端口；ItemRef 定位某个实体在该端口上的数据项。CallRef 标识调用节点；GrainRef 定位该节点对某个实体的逻辑计算。

这些二元坐标不表示生成完整笛卡尔积。Call/Port 与 Entity 必须匹配 Domain，运行时按需建立对应项。身份应在所属图/InputBatch 的上下文中解释；整数值不承诺跨 InputBatch 全局唯一。两个独立展开即使都产生页面，也可能属于不同 Domain。

```text
声明图中调用 RayModule → Call，产生一个或多个输出 Port
某个实体上的逻辑计算 → Grain，由 (CallRef, EntityRef) 定位
某个实体上的逻辑数据 → Item，由 (PortRef, EntityRef) 定位
若干就绪 Grains       → ExecutionMicrobatch → Worker
```

例如 `text, confidence = self.ocr(images, language=languages)` 创建一个 Call；images/languages 是输入连接，text/confidence 是两个输出 Port。Pipeline.forward 最后的 return 选择流水线输出，不额外创建 Call。

Grain、Item 首先是语义概念，不要求为每个名字新增包装类。实现只保留实际需要的 Ref、状态、记录和协议。

## 4. 状态与角色：解释清楚，避免成套换名

| 概念 | 边界 |
| --- | --- |
| GrainPhase | Grain 的执行阶段：READY、IN_FLIGHT、SEALED；SEALED 表示不再调度，不等于成功 |
| ItemOutcome | 数据结果：PRESENT 有值；DROPPED 被过滤或因必需输入被过滤而无值；FAILED 直接失败；SUPPRESSED 受失败影响而不采用正常结果 |
| generation | Grain 的执行代次，用于拒绝旧报告；重新入队时即递增，不等于已经实际执行的次数 |
| commit / publish / seal | 分别表示接受报告、建立逻辑事实、终结执行阶段；保留不同动作名称 |
| Engine | 推进一个输入批的逻辑状态 |
| DispatchState | 拥有就绪/恢复队列及 Grain 执行状态 |
| Executor | 管理 actor/RPC，并驱动多个输入批 |
| Worker | 持有 UDF 实例并处理执行微批；Ray actor 是远端宿主 |

WAITING 是依赖未决的概念状态，当前不是 GrainPhase 枚举成员。Item 的结果与 Grain 的执行阶段分开；逻辑屏蔽不意味着远端计算已经立即停止。

`RecordFailure`、`GroupFailure` 暂保留公开名称。前者对应一个 Grain 的业务失败；后者对同一 Call、同一直接父 Entity 的工作建立屏蔽规则，根 Entity 使用自身作用域。GroupFailure 不表示一个 ExecutionMicrobatch 整批失败，也不是全图取消。

## 5. 最小迁移表

下表为已完成的批次迁移与保留项；其余已完成的局部更名见 §6。

| 原名称 | 当前名称或决定 | 原因 |
| --- | --- | --- |
| Item、ItemRef、ItemRecord、ItemOutcome | 保留 | 与 Grain 区分数据和计算；Ref 字段已明确 Port 与 Entity，无需额外前缀 |
| Grain、GrainRef、GrainPhase、GrainRecord、GrainSnapshot、GrainInvocation 等 | 保留 | 计算粒度的语义已经明确 |
| Microbatch / MicrobatchEngine / MicrobatchMetrics | InputBatch / InputBatchEngine / InputBatchMetrics | 已完成；输入批统一前缀，保留 Engine/Metrics 职责后缀，不新增 InputBatch 包装类 |
| DispatchBatch | ExecutionMicrobatch | 已完成；明确一次物理执行微批 |
| microbatch_size / max_active_microbatches | input_batch_size / max_active_input_batches | 已完成；与输入批名称一致，同步 CLI 与结果字段 |
| Domain、Entity、Expansion 及对应 Ref | 保留 | 各自有独立语义，无需添加前缀或更换词根 |
| 编译产物、Spec、Effect、Layout、Binding、State、Record | 暂保留现名 | 后续只针对职责或真实歧义调整，不做整套同义更名 |

内部变量、错误信息和文档随确定的主词同步；不能全局替换所有含 item/batch 的文本。源数据行、Python 容器条目和局部明确的 batch 变量仍按实际语义命名。

不把名称变更扩大成新增抽象层、文件拆分或目录搬迁。命名阶段保留现有模块边界。

## 6. 其余命名审视：优先处理可验证的歧义

用户已批准下表中的五项局部更名，并明确保留 pre_init()。已实施项保持原有行为；其余建议继续逐项 QA。公开字段及 MinerU JSON 键的替换见 [API 迁移说明](api_migration.md)。

| 优先项 | 实际含义与问题 | 建议方案 |
| --- | --- | --- |
| 重试预算 `attempts` | 原参数允许额外 UDF 重试，容易被理解为总执行次数 | **已完成：** 参数 `max_retries`、配置字段 `max_udf_retries`；明确不含首次执行 |
| 指标 `grains` / `retries` | 前者包含重复 dispatch，后者在恢复入队时计数 | **两项均已完成：** `grain_dispatches` / `grain_requeues`；逻辑 `grain_count` 保留 |
| Worker 的 `lifetime_calls` | 非空批次进入处理就计数，可能早于 UDF 调用 | **已完成：** `lifetime_batches_received`；Worker 内部对应 `batches_received` |
| `DispatchState.is_idle` | 只检查队列是否为空，可以仍有 IN_FLIGHT Grain | **已完成：** `queues_empty`，布尔含义保持 |
| `pre_init` | 只记录 UDF 构造参数，不进行初始化 | **按用户要求保留原名与行为** |
| `CallTransition` / `call_transition` | 根据一个 Grain 的输入结果决定等待、就绪或传播失败；不是让静态 Call 改变状态 | 在状态机 QA 中评估 `InputDecision` / `resolve_inputs`，不扩大成全部 transition 类型改名 |

预算核对依据：`recovery.py` 的比较使用 completed_retries；`test/core/unit/test_recovery.py:242` 已覆盖次数 0、1 允许重试，次数 2 终止。`isolate_tail` 的一次整批重试之后还有递归拆分执行，不能把该参数描述成所有隔离执行的总次数上限。

仅需先补准定义的地方：

- **RayModule：** 声明 UDF 和配置；每次图中调用生成 Call，Executor 按 Call 建立 pool。已修正 README 中将 RayModule 直接等同 actor pool 的描述，暂不以 Operator 替换。
- **F.reduce：** 明确为沿父子关系有序收集保留的 Items，不接受求和等聚合函数。是否采用 gather 留到公开 API QA。
- **SEALED、generation：** 建议保留。前者表示执行生命周期终态，后者隔离旧报告；generation 在恢复入队时即递增，用 attempt_id 替换未必更准确。
- **GroupFailure 的 barrier：** 指 Call 与直接父项范围内的故障屏蔽规则，根实体用自身作用域；不是等待任务集合到齐的同步屏障。
- **架构文档：** materialization 实际位于 `_runtime/materialize.py`；RayModule 的调用建立静态 Call，Grain 随运行时 Entity 产生。已修正文档边界，未创建新类或搬动文件。

已同步 Executor、Worker、MinerU runner、测试和公开迁移说明；本轮不改变重试预算、计数时机或状态转换。批次迁移亦已完成；其他接口调整继续单独确认。
