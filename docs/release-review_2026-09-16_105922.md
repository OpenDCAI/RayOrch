## 1. 论文真正要求保留什么

| 论文合同 | 当前对应实现 | 结论 |
| --- | --- | --- |
| Domain / Entity / Port / Item / Call / Grain / Expansion 的不同身份 | `_model.py`、`_runtime/state.py` | 保留语义区分；不能统一成一套泛化 Node/Task 身份 |
| 编译期检查 Domain、依赖与结构关系 | `_builder.py`、`_program/` | 保留静态校验和预编译 Effect，避免运行时重读逻辑来源 |
| 单调的 Entity / Item / Expansion 事实 | `MicrobatchEngine` 的三个 `_publish_*` 入口 | 保留唯一发布者及完整记录写入后才入队的顺序 |
| 每 Call 的 FIFO Ready Queue、跨父项批处理 | `DispatchState`、`Executor` | 主路径已保留 |
| 同父项批处理与 FIFO 消融 | 原 multigrain 分支 | 按用户确认留在归档分支；release 无需恢复 |
| 物理阶段和逻辑结果分离 | `GrainPhase` 与 `ItemOutcome` / `ExpansionOutcome` | 必须保留；重试不能撤销已发布事实 |
| Grain 身份固定、generation 隔离旧尝试 | `_runtime/dispatch.py`、`engine.commit_reports` | 主实现和既有测试保留 |
| 按父项和 ordinal 归并，空集合是成功终态 | `_try_reduce`、`NestedGroupLayout` | 主路径存在；组合空分组的边界有错误 |
| GroupFailure 仅影响一个 Call × 直接父项 | `_SuppressionBarrierIndex` 和提交/预留入口 | 主路径存在；全屏蔽批次的基础设施恢复分支遗漏终态化 |
| 框架无关的持久 batch UDF | `_execution/worker.py`，`__init__` + `run` | 与论文 §5 对齐；应补清楚用户合同 |

论文要求的是状态和边界，不规定 Python 文件数，也不要求每个名词都变成一个可继承基础类。

### 状态所有权应保持如下结构

| 状态 | 唯一所有者 | 合法变化 |
| --- | --- | --- |
| 逻辑图和静态派生信息 | Builder / Compiler | 声明 → 校验 → 不可变 RuntimePlan |
| Item / Expansion / Entity 事实、lineage、屏蔽原因 | Engine | 未决 → 一个终态；同值重放幂等 |
| Grain phase、generation、待调度和恢复队列 | DispatchState | WAITING → READY/SEALED；READY → IN_FLIGHT；IN_FLIGHT → READY/SEALED |
| actor、容量、pending RPC、连接生命周期 | Executor / Ray adapter | 创建 → 使用/替换 → 释放 |
| 模型对象和 batch 计算 | Worker / UDF | 初始化 → 多次同步运行 |

将这些合进一个“大状态机”会让物理重试和业务终态相互影响，破坏论文的语义。适宜合并的是同一所有者内部的重复路径。

## 2. 发布前发现

P1：建议本次 release 前关闭。P2：需要明确处理或收敛；不等于要求重写。

### F1 · P1：全批次被屏蔽后，基础设施恢复遗漏 SEALED

位置：`rayorch/_runtime/engine.py:762–772`。

触发：同一父项的两批子项已经发出；第一批返回 GroupFailure；第二批随后发生 actor/transport 故障。第二批中已经没有 live Grain。

`_seal_and_publish_suppressed(barriered)` 位于 `if live is not None` 内部，因此这一分支返回 `0`，却保留 `IN_FLIGHT`。复现输出为：

```text
retried=0, late_phase=IN_FLIGHT, ready=0, complete=False
```

Executor 已移除对应 pending RPC，后续无法正常退休该 microbatch；没有待入场输入时会报告 deadlock，有待入场输入且 active credit 被占满时还可能一直空转。

建议：先预检仍存活部分的重试预算，再把屏蔽部分的 seal/publication 放入所有获准分支都会经过的共同路径。保留预算耗尽时不产生部分状态写入的保证。

这段函数与 v3_6 基线去除文档后的 AST 完全一致，是继承问题。修复后建议回补归档实现，避免论文参考实现和发行版对同一输入给出不同恢复结果。

### F2 · P1：Filter 丢失分组深度，合法嵌套归并会失败

位置：`rayorch/_program/analysis.py:98–103`；结果在 `_runtime/engine.py:1046–1065` 暴露。

`group_depth()` 将所有非 Reduce Port 的深度设为 0，忽略了 Filter/Broadcast 是透明值视图。运行时又在非空情况下读取 `NestedGroupBinding.layout.depth`，空值时依赖静态 `value_depth`，形成两个不一致的形状来源。

复现图：三层 expand → 内层 reduce → 全 true filter → 再两层 reduce。输入为一个根项，含一个空文档和一个非空文档：

```python
roots = [[[], [[1]]]]
```

过滤不应改变任何值，预期结果仍是 `[[[], [[1]]]]`，实际抛出 `ValueError: nested children must have one canonical depth`。

建议：完整传播结构视图的分组形状，统一空/非空归并的形状合同，覆盖 Filter、Broadcast、被 expand 的 group Port、零成员/零 survivor 的组合。避免只给某个调用点补临时分支。

`group_depth()` 与基线 AST 也相同。这直接涉及论文 §4.2 的空 Expansion 和有序嵌套归并。

### F3 · P1：返回值使用私有状态，丢失失败原因

位置：`rayorch/_runtime/materialize.py:57–59`、`rayorch/result.py:38`、`rayorch/__init__.py`。

UDF 返回 `RecordFailure('bad input')`，最终只得到 `rayorch._model.ItemOutcome.FAILED`。`RunResult` 没有保存 cause，调用者也不能从包根导入 ItemOutcome；旧 v3_6 曾公开该枚举。

这使用户无法只依赖公开 API 区分过滤、直接失败、下游屏蔽及其原因。更不应要求用户遍历 `compiled.logical`、Engine 私有表或根据枚举字符串判断。

建议：至少恢复公开结果状态。更完整的收敛方式是在结果边界提供状态、原因、来源坐标的公开不可变记录，保持内部 Ref/Engine 私有。无需同时公开全部协议 DTO。

### F4 · P1：安装后的 MinerU 命令找不到源码根

位置：`rayorch/benchmark/mineru/job.py:165–168`、`:99–100`。

README 从 `pip install rayorch` 引出 `rayorch-mineru-job`，但默认 `--project-root` 是 `Path(__file__).parents[3]`。安装后它指向 site-packages，而 `create_bundle` 强制要求那里存在 `pyproject.toml`。

已构建 wheel、解包到独立安装目录，并从该目录执行入口的参数解析/打包准备，复现：

```text
FileNotFoundError: RayOrch project root is invalid: .../installed
```

建议：区分“从已安装发行物提交”和“从开发源码构建 wheel”，不要依靠安装路径反推项目根。若本次仅支持源码启动，README 必须明确 clone、安装方式及 `--project-root`，并相应收窄命令承诺。

此外，通用 `build_wheel` 使用 `--no-build-isolation`，但普通安装未声明 launcher 的构建依赖；仅清空 requirements.txt 也不能通用于在 pyproject/setup.py 静态声明依赖的第三方包。该函数应缩小为已知源码布局的 staging 工具，或正式使用显式 wheel 输入。

### F5 · P1：发布版本仍与已存在的 0.0.1 相同

位置：`rayorch/version.py:1`、`.github/workflows/python-publish.yml`。

此次构建实际生成 `rayorch-0.0.1.tar.gz` 和 `rayorch-0.0.1-py3-none-any.whl`；PyPI 已于 2026-04-05 发布同名产物。当前变化还删除了旧 API/目录。必须决定新版本，并记录迁移方式；release tag 应与包元数据交叉校验。

来源：[PyPI 的 RayOrch 发布记录](https://pypi.org/project/rayorch/)。

### F6 · 范围说明：消融由归档分支复现；真实 adapter 的发布范围需明确

位置：`_program/lowering.py:293–299`、`_runtime/dispatch.py`、`_execution/executor.py`、`benchmark/`。

- 论文 §4.3 和基线支持 elastic / parent-bound reservation；release 拒绝 `batching_policy='single_parent'`。按用户确认，这属于有意精简，无需恢复。
- 基线 `ready_queue_order='unordered'` / `ready_fifo=False` 的 FIFO 消融路径保留在原 multigrain 分支。release 保留默认 FIFO，消融复现不属于 release 包职责。
- 当前只发布 MinerU 真正的 UDF/runner。Docling、Video、双模态只有 synthetic topology 测试，没有同等真实模型适配器。
- 原 v3_6 的 Docling/Video adapter 本身导入了 v3 的 business UDF。原样搬回会恢复跨版本依赖，不能解决维护边界。

release 无需恢复 parent-bound、unordered 队列或相关策略抽象。论文消融及原始实验通过原 multigrain 分支的固定提交复现，文档提供清楚的入口即可。需要发布的 Docling/Video UDF 应迁移到各自惰性插件，依赖业务包和公开 RayOrch API，不再导入 experimental/v3。

release 的目标是保留论文主路径的运行时语义；完整消融实验由归档分支承担。真实模型 adapter 与 synthetic topology 测试的区别仍需在文档中准确说明。

### F7 · P2：通用 Worker 仍探测 OCR/Table 字段，benchmark 依赖编译器内部

位置：`_execution/worker.py:231–240`、`benchmark/mineru/runner.py:202–206`。

Worker 自动读取 `last_table_batch_audit`、`last_ocr_batch_audit`，是可确认的业务耦合。MinerU runner 用 `compiled.logical.calls` 和 UDF 对象身份寻找 OCR 指标，也把 compiler 表结构带到了业务层。

建议统一可选的 `batch_audit()` 接口，由 UDF adapter 负责适配旧字段；Call 指标通过公开 stage 名称或稳定的执行描述查询。两项都可以通过很小的接口收敛完成，无需新增框架注册/反射体系。

### F8 · P2：观测操作可以无限阻塞已完成的业务结果

位置：`_execution/executor.py:298–341`。

`_observe_workers()` 自称 best effort，但 `ray.wait` 无 deadline。用户 `batch_audit()` 挂住或 actor 卡死时，业务已完成的 `run()` 仍不返回。应给观测总超时，把未完成观测记录为错误/缺失，不改变业务结果。此项为控制流确认，未人为挂住远端 GPU 作业来验证。

### F9 · P2：符号 Port 在 Python 条件里被静默当成 True

位置：`rayorch/api.py:14–19`。

`if port:` 能通过 trace，即使运行输入是 False，仍固定选择 Python 的 true 分支。对于明确的静态 DSL，建议 `Port.__bool__` 明确拒绝，并指向 `F.filter` 或普通配置期条件。无需为此增加动态图/控制流解释器。

### F10 · P2：新维护者入口与自动发布检查不足

- 当前只有 102 行 README、29 行核心架构说明和 64 行 benchmark 说明。缺少论文术语映射、状态转移表、一个完整子项生命周期、UDF 多输出/失败/可选输入合同、支持环境和迁移说明。
- README 的开发安装只是 `pip install -r requirements-dev.txt`；该文件没有安装当前项目，所以源码目录外未必能导入当前 checkout，也不会为它建立 CLI。
- 唯一 GitHub workflow 是 release build + twine + publish，没有 pytest，也没有 wheel 安装后的 smoke test。
- sdist 实际没有 docs、tests、requirements-dev.txt；包能构建，但拿源码包无法按 README 完成维护验证。
- 测试按 core/benchmark 分组，benchmark 下混有真实 Ray 测试；现有 cpu/gpu/api markers 没有构成清晰的默认测试入口。
- 非 UTF-8 Windows 环境中，两个源码检查测试因 `Path.read_text()` 未指定编码失败，另有三个测试使用 POSIX 路径/字符串假设。需要声明支持平台，并保证不涉及 GPU 的开发检查可重复执行。

建议恢复一个精简版 maintainer guide，而不是原样复制全部历史文档。PR 检查和 release 检查共用相同命令；GPU 实验按显式入口独立运行。

## 3. 设计模式和类数量评估

当前发布包：41 个 Python 文件、6,881 行（包含空行/注释）、117 个类，其中 80 个 dataclass、13 个 Enum、2 个 Protocol。真正业务继承仅有 `MinerUPipeline(Pipeline)`，其余继承主要是异常和枚举。

### 建议保留

1. **Pipeline / RayModule 外观和声明式组合。** 普通推理类只需初始化和 batch run，符合论文 §5。
2. **LogicalProgram → RuntimePlan 的固定编译管线。** 编译时处理结构，热路径查预编译索引；目前没有通用 PassManager 的负担。
3. **单写者事实引擎与独立 DispatchState。** semantic outcome 和 physical attempt 有不同生命周期。
4. **纯 transition 函数。** 可以穷举测试；比把条件分散在 Worker/Executor 中更容易维护。
5. **Worker 的值边界和薄 Ray adapter。** Worker 不知道 parent/ordinal，不操作 Engine。
6. **失败 sentinel、明确 recovery policy 和提交前预检。** 保留多输出原子性和 generation fence。
7. **有类型的 Ref 和边界 DTO。** `ItemRef` 和 `GrainRef` 即使外形相近，也承担完全不同的状态职责；省掉它们的名字会损害可读性。

### 可以精简的地方

| 改进 | 当前负担 | 建议的收敛 | 功能保护 |
| --- | --- | --- | --- |
| 恢复工作路径 | Executor 先取 live batch 作决策，Engine 再 partition；UDF/infra 各自处理屏蔽 | 共用 partition → 预算预检 → 屏蔽终态化前置步骤；后续保留不同 retry budget/actor 操作 | 全 live、混合、全屏蔽、预算耗尽、旧 generation |
| 形状事实 | 编译期 value_depth 和运行时实际 binding.depth 两套判断 | 一份完整的静态形状推导；group layout 组合集中成纯 helper | 任意多层 expand/reduce + filter/broadcast + 空集合 |
| 观测边界 | Worker 的业务字段探测；runner 访问 compiler 表 | 一个可选 audit 方法；公开 stage 标识和指标；观测限时 | 不改变派发或输出 |
| explanation | 默认构建完整逐 Port explanation，并随 CompiledProgram 保留四种视图 | explain 请求时再生成调试表示；正常 Executor 只依赖 plan | 保留 explain 输出和诊断能力 |
| Call 输入引用 | `CallUse(call,input_index)` → `CallInputEffect(call,input_index)` 纯换壳 | 可评估复用一个编译期不可变输入边描述 | 不把逻辑 Origin 暴露给 Engine；收益小，低优先级 |
| 只转发的函数 | `broadcast_transition(source)` 原样返回，薄 `_pool` 等路径 | 只在消除跳转确实帮助阅读时内联 | 不动真正有规则的 call/filter/reduce transition |
| 惰性导入样板 | mineru 的 `_MODULES` 逐一列出可直接导入的轻量子模块 | 可以只支持常规显式子模块 import，保留真正的 registry 延迟加载 | import rayorch 和 pipeline 均不能加载模型包 |

不要为消除几十行而引入 `BaseOperator`、`BaseEngine`、通用 `StateMachine`、插件化编译 PassManager 或多层 backend factory。现有薄适配器已经给推理框架留下足够的扩展点。

## 4. 有证据的执行路径优化

### 与 PR #9 的区别

已核对 Git 历史中 `f1c4ebc`（`perf(v3.6): partition dispatch queues by call (#9)`）的实际 diff。它将 microbatch 全局 Ready deque 改为 Call → deque，避免为某个 Call 派发时扫描其他 Call 的 Grain，正常 elastic reservation 因而只需按 batch 大小取队列元素。当前代码已保留这项优化。

本节的 Reduce 扫描发生在上游报告提交、`advance()` 传播事实的阶段，属于父项成员完成检查，和派发队列的查找不是同一个环节。下面的计数来自已经使用 per-call 队列的当前分支，而且只有一个父项，所以进一步按 Call 分区也无法消除该扫描。两项优化互补；不应撤销 PR #9，也不应把归并瓶颈误归因于它未实施。

参考：[PR #9](https://github.com/OpenDCAI/RayOrch/pull/9)。网页读取未成功，结论以本地 Git 对应提交的实际 diff 为依据。

### 4.1 Reduce 在逐项完成时有平方扫描

`_try_reduce()` 每次被触发都重新构建整个父项的 member/value 列表。用一个父项、batch size 1 的合法执行，统计传给 `reduce_transition` 的成员槽位数：

| 子项数 N | reduce_transition 调用数 | 检查成员槽位数 |
| --- | --- | --- |
| 32 | 33 | 1,056 |
| 64 | 65 | 4,160 |
| 128 | 129 | 16,512 |

该场景为 N(N+1) 量级，尚不包括 value 列表和判断的额外遍历。这是操作数量证据，不是 GPU 吞吐测量。

建议分两步：

1. 在一次 `advance()` 内合并对同一个 `(reduce target, parent)` 的重复触发，只在传播固定点需要时求值。可减少同批完成产生的重复工作。
2. 如果大父项仍是瓶颈，为 pending membership/value 增加可重建的增量索引；canonical Item/Expansion 表仍是事实来源。保留 survivor 按 ordinal materialize 的顺序。

第二步可能增加少量索引，但会缩短每个事件的实际工作；以复杂度与唯一事实来源衡量精简，而不以字典个数衡量。

### 4.2 Broadcast 从源反查目标会扫描整个 Domain

位置：`_runtime/engine.py:1077–1087`。

每个 ancestor Item 完成时遍历目标 Domain 的所有 Entity，再沿 lineage 判断祖先。延迟完成的 metadata 与大量跨父项子对象并存时，这会产生不必要的全域扫描。

可为静态广播关系建立 `(target domain, ancestor entity)` 的后代索引，在 Entity 发布时维护。它属于派生查询索引，不是新的业务状态所有者。用不同完成顺序验证语义等价，再测量实际改善。

### 4.3 清楚说明有限输入与内存边界

`Executor.run()` 先把完整来源转为 tuple，再预切全部 slices，最后保留所有结果到返回。这符合论文的有限 microbatch 范围，但不提供无界 streaming。可以在同一有限输入合同内惰性生成 slice、降低中间副本；输出迭代接口若要增加，应另行设计资源生命周期，不作为本次 release 的顺手重写。

## 5. 推理框架接口判断

**同步、有限、按 batch 返回值的模型 UDF，与论文 §5 一致，适合保留为唯一核心合同。**

需要公开说明：

- 类的 `__init__` 在 actor 内运行，模型加载由 persistent actor 摊销；`pre_init` 仅记录构造参数。
- `run` 或 callable 收到的是列式 `list`；每个输入列长度相同，输出对应 Grain 行，多个逻辑输出是 tuple-of-columns。
- 1:M 是一行里返回 list，再通过 `F.expand` 暴露子项；不能返回任意平铺长度替代 input/output arity 合同。
- 普通模型推理过程不接触 Ref/Domain/parent ID。顺序、父项完成和失败屏蔽归 RayOrch。
- async coroutine、generator/token streaming、跨 microbatch join/window、feedback 不属于当前接口；论文也明确限制在有限、无环结构。
- 重试可以重复调用 UDF；外部写入不能被误认为具备 exactly-once 保证。持久模型与副作用的幂等性需要在 adapter 文档中明确。
- `ray_options` 中哪些是 RayOrch 保留项、哪些原样传给 Ray，以及每个 UDF group 的 runtime_env 部署方式。

建议提供一个不需要 GPU 的模板示例和一个真实模型 adapter 示例。vLLM、Transformers、SGLang 等差异留在 adapter 的初始化/运行部分；不应让它们进入 Engine，也不需要先统一所有模型框架的基类。

当前跨框架兼容性的证据限于代码边界、既有 synthetic Ray 拓扑测试以及 MinerU adapter 的静态检查。本次没有执行真实 vLLM/Docling/视频 GPU 回归，不能用 118 项通过替代这些验证。

- **意义：** 减少批次遍历和临时元组构造，更主要是把“划分 → 纯策略判定 → 应用”放在拥有状态的同一入口，减少 Executor 对恢复内部步骤的编排。
- **已批准方案：** Engine 接收现有 RecoveryPolicy，只划分一次，再调用其纯 decide_udf() 并应用结果；Executor 保留失败分类、异常包装、actor 生命周期和计数。复用现有基础设施恢复的 int/None 返回约定：None 表示应中止且未修改状态，0 表示已处理但未重排任务；不新增状态类、分区缓存或策略层。
- **复杂度边界：** 对 K 个 Grain，仍为 O(K) 时间与 O(K) 最坏临时空间；只减少重复扫描/分配和入口数量，不宣称渐近复杂度提升。必须保留 ABORT 前无状态修改，以及全屏蔽批次照常封闭发布的语义。

- [x] **边界：** 全屏蔽批次无需询问 UDF 策略，直接封闭发布；存在可恢复任务且策略 ABORT 时，屏蔽成员也不会提前修改。重试次数不因分区重置，隔离按剩余 live 数量判断单项失败或二分。

### QA-10：展开子项绕过 MISSING 输出检查（待确认）

### QA-11：有后续输入时，停滞执行可能无限空转（待确认）

- **问题：** Executor.run() 在无 pending RPC 且还有未入场 slice 时直接 continue，未确认活跃批次是否还有入场容量。如果活跃容量已满、批次未完成且无法派发，也没有任何 RPC 能带来进展，会持续跳过后面的 deadlock 检查。
- **复现边界：** 对真实 Executor.run() 注入一个 `is_complete=False`、无法派发、无在途 RPC 的停滞批次；input_batch_size=1、max_active_input_batches=1。单行输入在首轮报 deadlock；两行输入只入场第一批，连续 5 轮仍为 active=1/pending=0，探针主动抛出终止异常以避免无限执行。未修改源码；这是故障注入，尚未找到合法正常图在前述修复后进入该状态的复现。
- **意义：** 保证真正无进展时明确失败，避免内部状态问题表现为 driver 忙循环。先前 F1 的停滞触发已修复，但 Executor 此处的错误循环条件仍存在。
- **建议：** 只有确有剩余容量、下一轮能够接纳新批次时，才因后续输入继续循环；保留已有 cleanup-only made_progress 路径，其余无进展情况进入现有 deadlock 报错。不增加超时、重试或新状态机。
- [ ] **实施与验证：** 待用户确认；应覆盖容量满且停滞、完成后释放容量、cleanup-only 推进，以及普通多 InputBatch 执行。
